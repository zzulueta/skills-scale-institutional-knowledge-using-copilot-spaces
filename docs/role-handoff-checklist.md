# Role Handoff Checklist

## Purpose
This checklist ensures clear handoffs between roles by defining required artifacts and verification steps. Use these checklists when work transitions from one team or role to another.

---

## Design → Development Handoff

Use this checklist when UX/Design hands off to Developers.

- [ ] **Annotated designs provided** — High-fidelity mockups with spacing, colors, typography, and interaction notes
- [ ] **Acceptance criteria defined** — Clear, testable criteria for visual and functional behavior
- [ ] **Accessibility specs included** — WCAG compliance notes, focus order, screen reader labels, and color contrast
- [ ] **Design assets available** — Icons, images, and fonts exported and accessible to developers
- [ ] **Edge cases documented** — Loading states, error messages, empty states, and responsive breakpoints
- [ ] **Design review completed** — Developers have reviewed designs and clarified open questions

---

## Development → QA Handoff

Use this checklist when Developers hand off to QA for testing.

- [ ] **Acceptance criteria present** — Feature meets all acceptance criteria defined in the ticket or design
- [ ] **Test data provided** — Sample data, user accounts, or test scenarios documented and accessible
- [ ] **Automated tests passing** — Unit and integration tests pass in CI; test coverage is adequate
- [ ] **Environment ready** — Feature deployed to test/staging environment and accessible to QA
- [ ] **Known limitations documented** — Any incomplete work, known issues, or dependencies noted
- [ ] **Demo or walkthrough completed** — Developer demonstrates feature and answers QA questions

---

## Release → Support Handoff

Use this checklist when releasing features to production and handing off to Customer Support.

- [ ] **Release notes drafted** — User-facing changes documented with clear descriptions
- [ ] **Knowledge base updated** — FAQs, troubleshooting guides, and feature docs updated
- [ ] **Monitoring and runbook links provided** — Links to dashboards, logs, and incident runbooks
- [ ] **Rollback plan documented** — Clear steps to rollback if critical issues arise
- [ ] **Support team briefed** — Live walkthrough or training session completed for customer-facing changes
- [ ] **Escalation path confirmed** — Severity tags, escalation contacts, and on-call rotation communicated

---

## How to use this checklist
- Copy relevant sections into project documentation or ticket templates.
- Adapt checklist items to fit your project's specific needs.
- Review checklists during planning to ensure all handoff requirements are achievable.
